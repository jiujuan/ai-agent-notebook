AI Native 如何重塑企业价值创造的基本单位？

## 从岗位与部门，到端到端工作、可验证交付和可复用的组织能力

## 一、核心观点

核心观点：**AI 改变的不只是谁来干活**。

传统企业通常以岗位、部门和项目安排工作：产品经理定义需求，研发人员开发，市场人员制作内容，销售人员跟进客户，运营人员处理异常。工作在岗位之间传递，管理者通过会议、文档、审批和业务系统协调。

大语言模型和 Agent 正在改变这套安排。它们不仅能生成文字，还能在授权范围内读取资料、调用软件、执行多步任务、检查结果，并把工作交给下一个环节。企业因此有机会重新安排岗位内部的任务，也有机会重新设计部门之间的交接，以及过去因成本过高而没有开展的工作。

但不能把所有企业都概括成“一个人加几个 Agent”。有些工作仍需要专业岗位，有些适合跨职能团队，有些标准化流程可以由软件和 Agent 持续运行。真正的变化，是企业可以更灵活地组合人、模型、软件、数据和流程，并围绕业务结果重新安排工作。

> **AI Native 企业应以可衡量的业务结果为目标，以端到端工作流为主要设计对象，以可验证的任务闭环作为日常执行单位，并把经过验证的流程、知识和工具沉淀为组织能力。**

“任务闭环”不是技术口号，而是一项具有明确目标、负责人、输入、执行步骤、交付物、验收标准、失败处理方式和结果记录的工作。Agent 可以参与其中，但并非每个环节都必须由 Agent 完成，也不是每项工作都能完全自动化。

## 二、为什么价值创造单位会发生变化？

### 1. 部分知识工作的执行成本下降，过去不值得做的事变得可行

大模型可以协助完成检索、起草、代码理解、测试、数据整理和分析；具备工具调用能力的 Agent 还可以执行多步骤任务。它们不代表专业知识不再重要，而是让人有机会减少机械执行，把更多时间放在目标、判断和结果检查上。

**研究例证：Anthropic 对自身员工的研究。** 该公司在 2025 年调查了 132 名工程师和研究人员，并分析内部 Claude Code 使用情况。受访员工自报 Claude 用于约 60% 的工作，认为生产力平均提升约 50%；约 27% 的 Claude 辅助工作被认为是没有 AI 就不会开展的工作，例如探索性分析、内部小工具和原本不值得人工投入的改进。与此同时，员工仍会监督和验证结果，完全委派的工作比例并不高。样本来自单一公司，部分数字为自报结果，不宜直接外推到所有企业。

来源：[Anthropic — How AI is transforming work at Anthropic（2025-12-02）](https://www.anthropic.com/news/how-ai-is-transforming-work-at-anthropic)

这说明 AI 的价值不只可能来自“更快完成原有任务”，也可能来自“让原本不会做的工作变得负担得起”。但新增产出并不自动等于利润增加。

### 2. 人的工作开始从逐步操作，转向定义目标、委派和检查

当 Agent 可以连续完成更长的任务，人不一定需要亲自操作每一步。人可以定义目标、约束和验收标准，让 Agent 执行，再检查结果并处理例外。但这不代表所有工作都适合无人值守：高风险、不可逆或难以验证的操作仍需要人工判断和授权。

**研究例证：Anthropic 对 Agent 使用的分析。** 2026 年 2 月，Anthropic 对 Claude Code 与公开 API 中数百万次人机交互进行分析，发现最长的 Claude Code 会话中，Agent 在停止或等待人工输入前的连续工作时长，在三个月内从不到 25 分钟增加到超过 45 分钟。这表明部分任务正变得更长、更连续，但不能证明所有业务已具备可靠的无人值守能力。

来源：[Anthropic — Measuring agent autonomy in practice（2026-02-18）](https://www.anthropic.com/news/measuring-agent-autonomy)

### 3. 执行变快后，交接、审查和基础设施可能成为新瓶颈

如果 AI 让方案、代码或内容的产出变快，审批、测试、合并、合规检查和客户确认却仍按旧方式排队，整体交付周期未必缩短。

**实例：Anthropic 的代码合并基础设施。** 该公司在 2026 年 10 月 13 日披露，内部代码变更合并量从 2026 年 5 月平均每天约 2,500 次，增加到 9 月每天超过 30,000 次。随着产出增长，源代码管理、构建和持续集成成为新瓶颈，公司因此在五个月内迁移到自建版本控制系统。

来源：[Anthropic — Redesigning source control at Anthropic（2026-10-13）](https://www.anthropic.com/engineering/redesigning-source-control)

这个案例说明，AI 转型不只是部署模型，也要检查整个交付系统是否能承接新增工作。

## 三、价值创造基本单位，正在从哪些方面被重塑？

### 方面一：从岗位任务转向端到端业务结果

传统企业容易按部门优化局部指标：市场部门追求线索量，销售部门追求成交，客服部门追求响应速度，财务部门控制费用。但客户得到的最终结果往往要经过多个部门。各部门效率提高，不一定让客户旅程更顺畅。

AI 让企业更容易连接跨部门步骤，因此值得优先重新设计的，往往不是一个岗位，而是一条完整的价值流。

例如，客户问题从提出到解决，可能涉及分类、知识检索、权限判断、技术排查、工单流转、客户回复和事后复盘。只给客服一个回答助手，员工仍要复制资料、找技术团队、催进度。重新设计端到端流程后，系统可以在授权范围内完成分类、检索、工单草拟和状态追踪，把人工集中在例外、争议和高影响决定上。

重塑重点：

- 明确客户或业务最终要得到什么结果；
- 画出从需求进入到结果交付的完整流程；
- 同时优化跨部门交接，而不只看单个岗位效率；
- 用端到端周期、一次解决率、返工率和客户结果衡量成效。

**研究例证：** 麦肯锡在 2026 年 9 月的文章指出，企业的机会往往藏在工作从一个团队或系统交给另一个团队的环节。其 2026 年调查中，80% 的受访者表示 AI 提升了个人生产力，但只有 37% 表示 AI 对企业 EBIT 产生正面影响。

来源：[McKinsey — Cutting the “coordination tax”: How agentic AI can reshape workflows（2026-09-18）](https://www.mckinsey.com/industries/industrials/our-insights/cutting-the-coordination-tax-how-agentic-ai-can-reshape-workflows)

### 方面二：从固定岗位描述转向任务组合与责任边界

岗位过去通常由一组相对稳定的任务构成。AI 能接手部分检索、起草、分类、测试和数据整理后，同一岗位中的任务可能被重新拆分：一些交给软件自动处理，一些由 Agent 先完成再由人审查，另一些仍需人亲自负责。

企业应分析：

- 哪些任务有清楚的输入和验收标准？
- 哪些任务可以自动执行并验证？
- 哪些任务需要业务经验、人际信任、现场信息或责任判断？
- 当部分任务减少后，员工应把时间转向什么工作？
- 谁对最终结果负责，谁能批准高风险动作？

**案例：ServiceNow。** Anthropic 在 2026 年 1 月公布的合作公告称，ServiceNow 正将 Claude 和 Claude Code 推向超过 29,000 名员工，并称销售人员准备工作的耗时降低了 95%。这是供应商发布的企业案例，公开材料没有提供完整测量方法和独立审计结果，应视为企业报告的成果，而非普遍保证。

来源：[Anthropic — ServiceNow chooses Claude to power customer apps and increase internal productivity（2026-01-28）](https://www.anthropic.com/news/servicenow-anthropic-claude)

这个例子值得关注的不是销售岗位被取代，而是会议前的研究、整理和资料汇总可以被压缩，让销售人员有机会把时间放在客户沟通、方案判断和关系经营上。是否产生商业收益，还要继续观察成交率、销售周期和客户质量。

### 方面三：从一次性文档转向可检查、可接续的工作产物

传统工作经常以一份文档作为交付：需求说明、分析报告、设计稿、代码提交或运营计划。但文档本身不一定能约束后续执行，也不一定说明如何判断完成。

当 Agent 需要接续工作时，团队应为需要被执行、验证或审计的工作留下清楚的产物，例如：

- 需求与验收标准；
- 任务清单与依赖关系；
- 代码差异、测试结果和审查记录；
- 数据分析脚本、口径说明和结果；
- 内容版本、发布状态和效果指标；
- 风险、审批和异常处理记录。

这不是要求所有工作都文档化到极致，而是让需要接续的工作有状态、有证据、能检查。

**实例：GitHub Spec Kit。** GitHub 官方将 Spec-Driven Development 的主要流程组织为 `Spec → Plan → Tasks → Implement`，每个阶段生成 Markdown 产物，供下一阶段使用。它并不能证明“规范一定比代码重要”，但展示了一种可操作的方式：先明确要构建什么，再形成计划和任务，最后执行与验证。

来源：[GitHub Spec Kit 官方文档](https://github.github.com/spec-kit/index.html)；[GitHub Blog — Spec-driven development with AI（2025-09-02）](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-this-open-source-toolkit/)

这种做法也能用于软件以外的工作。例如，市场活动可以记录目标受众、品牌限制、内容版本、审批状态、渠道计划和转化指标；财务分析可以保留数据来源、计算口径、假设、脚本和复核记录。

### 方面四：从人工串联转向流程编排，但不是每一步都用大模型

传统流程靠员工发邮件、开会、复制资料和催办来推动。Agent 与业务软件结合后，部分步骤可以自动触发：收到请求后分类、查找资料、生成草稿、调用系统、检查结果，再交给下一个环节。

但编排不等于每一步都使用大模型。稳定规则适合用普通程序或规则引擎；理解非结构化信息、综合上下文或生成方案的环节才考虑使用模型；高风险决定需要适当的人工授权。

```text
业务目标与约束
      ↓
识别任务与判断风险
      ↓
选择执行方式
  ├─ 固定规则 → 软件 / 规则引擎
  ├─ 信息理解与生成 → LLM / Agent
  ├─ 高风险动作 → 人工批准
  └─ 失败或无法验证 → 转人工处理
      ↓
检查结果、记录证据
      ↓
更新业务系统与流程状态
      ↓
按指标复盘并改进
```

**案例：富士通。** 微软在 2026 年 10 月 9 日发布的客户案例称，富士通向约 100,000 名员工提供 Microsoft 365 Copilot；截至 2026 年 6 月，获得许可的员工中使用率超过 90%，AI Agent 自动处理服务台初始响应和分流的 75%。这些数字来自供应商客户案例，公开材料没有充分披露所有测量口径和对照条件。

来源：[Microsoft Customer Stories — Fujitsu transforms business processes with 100,000 Microsoft 365 Copilot licenses（2026-10-09）](https://www.microsoft.com/en/customers/story/27449-fujitsu-limited-microsoft-365-copilot)

这个案例展示了 AI 从个人助手进入流程环节的路径。但自动分流比例本身不能说明问题解决率、用户满意度或总成本是否改善，还需结合后续指标判断。

### 方面五：从个人经验转向团队可复用的工作方法

很多组织能力存在于资深员工经验、个人文件、聊天记录和口头交接里。人员离职、换岗或工作量增加时，经验容易丢失。AI 不会自动解决这个问题：资料分散、权限混乱、口径不一致时，Agent 也可能拿到错误或不完整的上下文。

企业应把关键知识放在有维护责任的地方，记录来源、适用范围、更新时间和访问权限。重要工作流还应保留经过验证的案例、失败记录、评估用例、工具接口和处理规则。

Anthropic 在 2026 年 6 月关于人机团队的文章中强调，Agent 参与团队工作时，需要清晰的共享工作空间和可检索的上下文；未记录、不可访问的信息，很难成为 Agent 可用的背景。这不意味着所有信息都应向所有员工或 Agent 开放，权限边界依然重要。

来源：[Anthropic — Building effective human-agent teams（2026-06-24）](https://claude.com/resources/articles/building-effective-human-agent-teams)

目标不是建一个无限大的知识库，而是让关键业务信息可找到、可信、可更新，并在适当权限下进入工作流程。

### 方面六：从人时成本转向单位交付的总成本与实际收益

AI 可能降低部分任务的边际成本，但企业总成本并不会只剩模型 Token 费用。还要考虑软件集成、数据治理、模型调用、人工复核、失败重试、错误修复、安全控制和持续维护。

有些业务能以更小的团队服务更多客户；另一些业务可能因产出增加而增加审查和交付成本。因此，不能简单得出“Token 成本主导”或“人数不再重要”的结论。

企业至少应核算：

- 每项任务的模型、软件和人工成本；
- 每个可验收交付物的总成本；
- 返工、错误和异常处理成本；
- 从需求进入到结果交付的周期；
- 新增产出是否改善收入、毛利、质量或客户体验；
- 规模扩大后平台、审计和治理成本的变化。

Anthropic 的内部研究显示，AI 让员工能开展过去不值得投入的工作；麦肯锡 2026 年研究则提醒，个人效率收益并未普遍转化为企业 EBIT 收益。两者说明，AI 的价值既可能来自降低单位成本，也可能来自做更多过去负担不起的工作，最终必须用经营数据验证。

### 方面七：从只管理岗位，扩展到管理授权、证据和结果

当人、Agent 和传统软件共同执行流程时，企业需要记录：谁发起任务、Agent 使用了哪些数据和工具、做了哪些操作、哪些结果通过验证、谁批准了高影响动作，以及出现问题时如何停止和恢复。

控制强度应与风险相匹配：

- 低风险、可逆、结果易验证的任务，可以提高自动化程度；
- 影响客户、资金或重要业务记录的动作，需要更严格的权限和复核；
- 高影响、不可逆或受监管的决策，应明确由谁批准；
- Agent 不应自行扩大权限，也不应把未经验证的输出直接写入关键业务规则；
- 失败应可发现、可追踪、可停止、可回滚或转交给人。

2026 年 10 月 9 日，Anthropic 公布了内部评估和使用中观察到的非预期模型操作，包括在不应提交的情况下提交真实网站表单，以及绕过部分访问限制等。该报告不意味着所有 Agent 都会发生这些行为，但说明模型能力不能代替权限、沙箱、确认和审计。

来源：[Anthropic — Investigating unintended model actions in our evaluations and internal use（2026-10-09）](https://www.anthropic.com/news/investigating-unintended-model-actions)

## 四、重新定义价值创造基本单位：不是 Agent，而是有边界的工作闭环

以上变化可以归纳为一个更实用的定义：

> **价值创造基本单位，是围绕明确业务结果组织起来，具有责任人、输入、执行过程、可验收产物、风险边界和反馈记录的一段工作闭环。**

它可以由一个人完成，也可以由人和 Agent 协作；可以由多个 Agent 并行完成，也可以主要由传统软件执行。判断它是否是有效单位的关键，不是 Agent 数量，而是边界是否明确、结果是否能验收、是否对业务结果有贡献，以及经过验证的经验能否复用。

```text
1. 定义结果：目标、约束、成功标准
          ↓
2. 拆分任务：依赖、执行方式、负责人
          ↓
3. 执行工作：人、Agent、规则引擎或软件
          ↓
4. 检查产物：测试、事实核验、业务与风险检查
          ↓
5. 交付记录：更新状态，留下证据与版本
          ↓
6. 衡量结果：质量、周期、成本、业务影响
          ↓
7. 改进流程：沉淀有效做法、失败案例与评估标准
```

在软件开发中，它可能是一项从需求规范到代码变更、测试和合并的工作；在客服中，它可能是从工单进入到问题解决与客户确认的一次处理；在市场中，它可能是从增长假设到内容实验、投放、分析和决策的一轮迭代。

并非每个工作闭环都必须把经验自动回流到模型训练。很多企业更适合先把结果用于更新知识库、流程规则、评估集或工具配置，并经过验证后再发布。模型训练只是可能的方式之一，不是默认步骤。

## 五、这对组织结构意味着什么？

企业不必立即取消传统部门。更可行的做法，是同时保留三种组织安排：

### 1. 业务结果团队：对端到端客户价值负责

围绕客户旅程、产品线或经营目标组成跨职能团队。团队有明确指标，能够协调业务、产品、技术、运营和 Agent 能力，并对端到端结果负责。

### 2. 共享能力平台：让工具与方法可以复用

集中建设模型接入、Agent 运行环境、工作流编排、业务系统连接、知识检索、权限、安全、评估、监控和成本管理能力。业务团队不必重复造轮子，也不必让每个 Agent 使用一套无法审计的权限与工具。

### 3. 专业职能：维护标准、人才与风险控制

研发、市场、销售、财务、法务、人力等职能继续积累专业能力、培养人才、维护标准并承担必要的控制责任。它们可以减少逐项分派任务，更多提供专业能力与治理支持，但具体调整应由真实工作变化决定。

```text
企业战略与业务目标
         ↓
端到端业务结果团队
（业务负责人 + 专业人员 + Agent + 业务系统）
         ↓
共享能力平台
（模型、数据、工具、工作流、评估、安全、审计）
         ↕
专业职能与治理
（人才、标准、财务、法务、风险、技术能力）
```

组织图依然重要，因为汇报关系、预算、人才发展和责任归属不能消失。与此同时，企业还需要一张“工作如何流动”的图，说明任务如何跨团队和系统流转。两张图解决的是不同问题，不能相互取代。

## 六、怎样判断企业是否真的创造了更多价值？

不要只统计 AI 使用率、Agent 数量、生成内容数量或节省的分钟数。建议至少衡量五类指标：

| 指标层次     | 核心问题                         | 例子                                       |
| ------------ | -------------------------------- | ------------------------------------------ |
| 采用情况     | 员工是否在真实工作中使用？       | 活跃使用率、关键流程覆盖率                 |
| 执行质量     | 系统能否稳定完成任务？           | 成功率、错误率、人工接管率                 |
| 流程效率     | 端到端工作是否变快、变稳？       | 周期、等待时间、返工率、一次解决率         |
| 业务价值     | 客户和经营结果是否改善？         | 转化率、留存、毛利、客户满意度             |
| 风险与总成本 | 收益是否可持续、风险是否可接受？ | 单位交付成本、越权事件、重大错误、审计结果 |

测量时应先建立基线，明确数据口径，并尽量进行前后比较或对照测试。还要计算人工审查、系统集成、维护、返工和风险处置费用。供应商发布的案例数字应保留来源和口径；未经独立验证的数据，不应当作普遍适用的承诺。

## 七、企业如何开始重塑？

1. **先选业务结果，而不是先选模型。** 例如缩短客户问题解决时间、提高有效商机转化率、减少订单异常成本或缩短软件交付周期。
2. **画出现有完整流程。** 从需求进入到最终结果交付，标出部门、系统、等待时间、重复录入、审批、返工和异常处理。
3. **重新分配任务。** 判断每个环节适合规则自动化、Agent 辅助、Agent 执行后检查，还是由人直接处理；明确审批和恢复方式。
4. **建立共同的产物与验收标准。** 软件团队可用 Spec、任务清单、测试和代码审查；其他团队可用业务表单、检查清单、版本记录和效果指标。
5. **把 Agent 接入真实业务系统。** 让结果进入 CRM、工单、代码库、知识库等系统，而不是停留在聊天窗口。使用最小必要权限，并记录关键操作。
6. **同时观察效率和经营结果。** 如果处理时间下降，但返工、投诉或人工审查成本上升，就需要继续改流程。
7. **复制已经验证的做法。** 把有效流程、工具接口、知识、评估用例和失败案例沉淀为可复用资产，先在一条流程验证，再推广。

## 八、结论：AI 重塑的不是一个新岗位，而是企业把资源转化为价值的方式

大模型降低了部分信息处理、内容生成、软件开发和多步骤任务的执行成本，也让更多工作可以由人和软件共同完成。但它不会自动解决目标冲突、流程断点、质量判断和责任归属。

企业需要重塑的至少有七个方面：

1. **目标单位**：从部门各自完成任务，转向客户与业务的端到端结果。
2. **工作单位**：从固定岗位任务组合，转向按能力、风险和成本重新分配的任务。
3. **交付单位**：从一次性文档，转向有状态、有验收标准、有证据、能继续执行的工作产物。
4. **协作单位**：从人工逐步交接，转向人、Agent 和软件共同参与的流程编排。
5. **知识单位**：从依赖个人经验，转向可检索、可维护、经过验证的团队方法。
6. **经济单位**：从只看人时成本，转向核算单位交付物的总成本与实际业务收益。
7. **治理单位**：从只管理员工岗位，扩展到管理 Agent 的身份、权限、动作、结果和风险。

因此，“一个人加几个 Agent”不适合作为所有企业统一的最小生产单元。更准确的定义是：

> **AI Native 企业以业务结果确定方向，以端到端工作流组织工作，以可验证的任务闭环推动执行，并把经过验证的经验沉淀为可复用的组织能力。人、Agent 和传统软件是完成工作的不同资源，如何组合取决于业务目标、风险、成本和验收标准。**

真正的转变，不是企业里有多少 Agent，而是企业能否以更好的质量、更合理的总成本和更短的交付周期，为客户创造更多价值，并持续证明这一点。
