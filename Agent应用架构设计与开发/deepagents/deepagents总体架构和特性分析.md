## 1️⃣ DeepAgents 的总体架构设计

从文档和 GitHub repo 来看，DeepAgents 是一个 **Agent Harness**，本质上是一个**多 Agent 协作框架**，其架构目标是让复杂任务可以通过多个子 Agent 协同完成，同时支持持久化、上下文管理和可扩展工具接入。

我们可以把它的架构理解为几个核心层次：

```
┌─────────────────────────┐
│      User / CLI / API    │ ← 人机接口
└─────────┬───────────────┘
          │
┌─────────▼───────────────┐
│   Orchestrator / Core    │ ← DeepAgents 核心调度
│ - Agent 管理             │
│ - 任务分配 / 调度        │
│ - 上下文路由             │
└─────────┬───────────────┘
          │
┌─────────▼───────────────┐
│    Sub-Agents / Skills   │ ← 任务执行单元
│ - 独立上下文             │
│ - 可复用技能             │
└─────────┬───────────────┘
          │
┌─────────▼───────────────┐
│   Tools / Memory / FS    │ ← 外部接口与持久化
│ - 文件系统访问           │
│ - 数据库 / 内存持久化    │
│ - Shell / MCP 接口       │
└─────────────────────────┘
```

关键特点：

- **模块化和可扩展性**：每个子 Agent 都有自己的上下文，工具和技能可以按需挂载。
- **任务分层与调度**：Orchestrator 负责将用户请求拆分为多个子任务，分配给不同 Agent。
- **持久化与上下文管理**：长会话或复杂任务可以跨 session 保存状态，避免信息丢失。
- **Human-in-the-loop**：保证关键操作可以有人工干预，提高安全性和可控性。

## 2️⃣ 特性分析及实现机制

### 2.1 Sub-agents（子 Agent）

- **功能**：可以将复杂任务拆分给不同 Agent，每个 Agent 有独立上下文。
- **实现方式**：
  - 每个子 Agent 有自己独立的内存和上下文窗口。
  - Orchestrator 可以通过规则或 LLM 生成的决策，将任务分发给不同子 Agent。
  - 有些子 Agent 可以是“技能 Agent”，只负责特定类型任务。
- **优势**：
  - 避免上下文冲突。
  - 支持并行处理，提高效率。

### 2.2 Filesystem（文件系统操作）

- **功能**：读写、编辑、搜索文件，可接入本地、沙箱或远程文件系统。
- **实现方式**：
  - 抽象出一个 **Pluggable FS Backend** 接口。
  - Agent 对 FS 的操作通过 API 调用或 RPC 完成，保证安全性。
  - 沙箱化执行可以防止恶意命令影响宿主系统。
- **优势**：
  - 可管理不同存储资源。
  - 可扩展为云端、数据库或本地文件系统。

### 2.3 Context management（上下文管理）

- **功能**：长对话或复杂任务中，自动总结上下文，减少内存占用。
- **实现方式**：
  - 使用 LLM 对会话或工具输出进行摘要。
  - 将总结后的信息或大块数据 offload 到磁盘或数据库。
  - 当 Agent 需要时，按需 reload 上下文。
- **优势**：
  - 支持长会话、多任务协作。
  - 避免 LLM token 限制带来的上下文丢失。

### 2.4 Shell access（Shell 访问）

- **功能**：Agent 可以在指定沙箱环境执行命令。
- **实现方式**：
  - 通过 sandbox 模块限制命令执行环境。
  - 可以记录和审计每条命令。
- **优势**：
  - 可处理自动化运维任务。
  - 增强系统可控性与安全性。

### 2.5 Persistent memory（持久化记忆）

- **功能**：跨会话记忆状态，可自定义存储后端。
- **实现方式**：
  - 抽象 Memory Backend（如 SQLite、Redis、云存储）。
  - Agent 的状态、技能调用结果或用户数据可以写入 backend。
  - 支持跨会话 recall。
- **优势**：
  - 长期任务可持续。
  - 支持多 Agent 共享或独立记忆。

### 2.6 Human-in-the-loop（人工干预）

- **功能**：在关键操作前允许用户批准、编辑或拒绝。
- **实现方式**：
  - Orchestrator 在调用工具前生成候选操作。
  - 等待用户确认后再执行。
- **优势**：
  - 增强系统安全性。
  - 对敏感操作可审计。

### 2.7 Skills（技能复用）

- **功能**：Agent 可以按需加载预定义行为（技能）。
- **实现方式**：
  - 技能封装为独立模块或函数。
  - Agent 可以按名称调用，Orchestrator 负责调度。
- **优势**：
  - 提高复用性。
  - 简化复杂任务的组合。

### 2.8 Tools（工具扩展）

- **功能**：接入自定义函数或 MCP（Multi-Channel Protocol）服务器。
- **实现方式**：
  - 通过标准接口注册工具。
  - Agent 在任务中可以直接调用这些工具。
- **优势**：
  - 高度可扩展。
  - 支持自定义业务逻辑或第三方服务。

------

## 3️⃣ 技术设计总结

1. **核心思想**：把 LLM Agent 变成一个 **可组合、可扩展、可持久化的任务执行单元**。
2. **模块化**：
   - Orchestrator → 管理和调度 Agent
   - Sub-Agent → 执行具体任务
   - Memory / FS / Tools → 数据和功能接口
3. **扩展性**：
   - 新的技能、工具、存储后端可以无缝接入。
4. **安全与可控性**：
   - 沙箱执行、人工审批、分离上下文。
5. **长期目标**：
   - 支持多 Agent 协作、多任务处理、跨会话记忆。
