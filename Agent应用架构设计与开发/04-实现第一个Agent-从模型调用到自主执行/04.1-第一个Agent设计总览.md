总览：实现第一个 Agent——从模型调用到 Agent Loop

## 一、为什么要亲手实现第一个 Agent？

在前面的学习中，我们已经认识了 LLM（大语言模型），了解了 Agent 的基本组成，也从整体架构的角度分析了一个 Agent 应用需要哪些技术层次。

但是，理解概念并不意味着能够开发系统。

当我们真正开始编写 Agent 应用时，会遇到一系列具体问题：

- 如何使用 Python 调用真实的大语言模型？
- 如果希望同时支持 OpenAI、Anthropic、DeepSeek 和 Ollama，应该怎样设计模型调用接口？
- 模型返回一段文本后，程序如何判断下一步应该继续执行，还是返回最终答案？
- 当模型要求调用工具时，程序怎样找到工具、验证参数并执行函数？
- 工具执行完成后，如何把结果交还给模型？
- 如果模型持续调用工具，或者某个工具执行失败，系统应该如何处理？
- 如何通过测试和运行日志，确认 Agent 的行为符合预期？

这些问题构成了 Agent 应用开发的起点。

本章将从一个最小可运行的 Agent 开始，逐步实现模型接入、工具调用、Agent Loop、异常处理和自动化测试。

> ⚠️：我们的目标不是直接开发一个复杂的企业级 Agent 平台，而是先掌握它最基本的运行机制，为后续构建 Agent Runtime、工具注册中心、任务状态机、记忆系统和多 Agent 协作系统打下基础。

**本章的核心目标：亲手实现一个真正调用 LLM、能够使用工具，并根据执行结果继续决策的 Agent。**

## 二、从单轮 LLM 到多步 Agent

### 2.1 单轮 LLM 应用是怎样工作的？

最简单的大模型应用只有三个步骤：

1. 接收用户输入。
2. 将输入发送给大语言模型。
3. 返回模型生成的回答。

其基本流程如下：

```
用户输入
   |
   v
构建提示词与上下文
   |
   v
调用 LLM API
   |
   v
获取模型回答
   |
   v
返回结果
```

例如，用户提出：

> 请帮我分析一下 Agent 与普通大模型应用有什么区别。

程序将问题发送给模型，模型生成解释，应用返回结果。

这种方式适合普通问答、文本改写、摘要生成和简单内容创作。

但是，当任务需要访问外部数据、执行计算、操作文件或根据执行结果调整行动时，单次模型调用就可能不够用了。

### 2.2 为什么需要 Agent Loop？

假设用户提出一个新的任务：

> 请计算 12345 与 67890 的和，然后将计算结果解释清楚。

如果程序只调用一次 LLM，模型可能直接生成答案。但这并不意味着程序真正执行过计算。

我们希望系统能够：

1. 让模型判断是否需要使用计算工具。
2. 根据模型返回的调用请求，执行真实的 Python 函数。
3. 获取工具的实际执行结果。
4. 将结果反馈给模型。
5. 让模型根据真实结果生成最终答案。

此时，系统的执行过程变成了：

```
用户提出任务
      |
      v
LLM 决定下一步行动
      |
      v
Agent 执行工具
      |
      v
获取真实执行结果
      |
      v
将结果反馈给 LLM
      |
      v
LLM 再次决策
      |
      v
判断是否完成任务
   /          \
  否            是
  |             |
  v             v
继续循环      返回最终答案
```

这就是 Agent Loop 的基本思想。

**Agent Loop 将模型决策、工具执行、结果观察和后续决策连接起来，使应用不再局限于一次性的文本生成。**

需要注意，Agent 不一定每次都要多轮调用模型。对于简单任务，一次调用就足够；只有当任务需要动态决策、外部执行或结果反馈时，多步循环才具有明显价值。

## 三、本章最终要构建什么？

本章将构建一个基于 Python 3 的最小 Agent 项目。

这个 Agent 能够接收用户任务，通过真实的大语言模型决定下一步行动，调用经过注册的工具，并在获取执行结果后继续运行。

### 3.1 预期功能

完成本章后，程序应具备以下能力：

| 功能             | 具体要求                                 |
| ---------------- | ---------------------------------------- |
| 模型接入         | 能够调用真实 LLM API                     |
| 多 Provider 支持 | 通过适配器支持不同模型服务               |
| 统一决策         | 使用统一的数据结构表示最终答案和工具调用 |
| 工具注册         | 根据名称发现已经注册的工具               |
| 参数校验         | 执行工具前检查参数是否合法               |
| 结果反馈         | 将工具执行结果交回模型                   |
| Agent Loop       | 支持多轮模型决策与工具执行               |
| 停止条件         | 支持最终答案和最大执行步数限制           |
| 异常处理         | 处理工具执行失败和模型调用错误           |
| 测试与日志       | 能够观察执行过程并验证核心行为           |

这里的目标是实现一个具备基本工程结构的 Agent，而不是一次性完成所有企业级能力。

例如，持久化任务状态、任务中断恢复、人工审批、复杂工作流和多 Agent 协作，将在后续章节逐步实现。

### 3.2 最终运行效果

我们希望最终能够运行类似下面的程序：

```
answer = agent.run(
    "请使用计算工具计算 12345 + 67890，"
    "并解释计算结果。"
)

print(answer)
```

程序内部可能发生如下过程：

```
[Step 1] 请求模型决策
[Step 1] 模型要求调用工具 add
[Step 1] 执行 add(12345, 67890)
[Step 1] 工具返回 80235

[Step 2] 将工具结果发送给模型
[Step 2] 模型生成最终答案

任务完成。
```

以上是用于说明目标的示例日志，不是某次真实 API 调用的记录。

与普通聊天程序相比，这个程序多了一个关键能力：它不仅能生成文本，还能根据模型的决策执行真实操作，并将执行结果反馈给模型。

## 四、整体架构：一个最小 Agent 由哪些组件组成？

为了避免所有逻辑都堆积在一个函数中，我们先将系统划分为几个职责明确的组件。

### 4.1 核心架构

```
                    用户
                     |
                     v
              +--------------+
              |  Agent Loop  |
              +--------------+
                     |
          +----------+----------+
          |                     |
          v                     v
   +-------------+      +---------------+
   | ModelClient |      | Tool Registry |
   +-------------+      +---------------+
          |                     |
          v                     v
   +-------------+      +---------------+
   | Provider    |      | Tool Executor |
   | Adapter     |      | 参数校验与执行 |
   +-------------+      +---------------+
          |                     |
          v                     v
    真实 LLM API             工具结果
          |                     |
          +----------+----------+
                     |
                     v
              结果反馈与更新
                     |
                     v
                下一轮决策
```

这张图展示的是逻辑职责，而不是要求每个模块都必须单独部署为服务。

在本章中，所有组件都可以运行在同一个 Python 进程内。

### 4.2 各组件分别负责什么？

**1. ModelClient：统一模型调用接口**

负责屏蔽不同模型供应商的调用差异，让 Agent 通过统一方法请求模型决策。

例如：

```
decision = model.decide(
    messages=messages,
    tools=tool_definitions,
)
```

Agent 不需要直接处理每个供应商的原始 SDK 响应。

**2. Provider Adapter：模型供应商适配器**

负责调用真实模型 API，并将供应商返回的数据转换成应用内部统一的消息与决策格式。

本章将介绍：

- OpenAI。
- Anthropic。
- DeepSeek。
- Ollama。

其中，OpenAI、DeepSeek 和 Ollama 可以在适配器支持且接口兼容的情况下共用相近的调用实现；Anthropic 则需要适配自己的消息和工具调用协议。

**3. Decision：统一决策结果**

负责描述模型下一步要做什么。

本章先支持两种基本决策：

- `final`：返回最终答案。
- `tool_call`：请求调用一个或多个工具。

通过统一决策结构，Agent 可以使用一致的逻辑处理不同模型的输出。

**4. Tool Registry：工具注册中心**

负责注册和发现工具，保存工具名称、功能说明、参数 Schema 以及对应的执行函数。

例如：

```
add
get_current_date
```

当模型请求调用 `add` 时，系统可以从注册中心找到对应工具。

**5. Tool Executor：工具执行器**

负责校验参数、调用已注册的工具函数、收集执行结果，并处理工具执行失败。

模型只能提出工具调用请求，真正的函数执行由应用运行时控制。

**6. Agent Loop：执行控制循环**

这是本章的核心组件，负责协调模型、工具和消息历史。

它决定何时请求模型、何时执行工具、如何反馈结果，以及何时终止任务。

## 五、为什么要设计统一的模型调用接口？

在实现 Agent Loop 之前，我们需要先解决多模型接入问题。

假设应用直接依赖某一个供应商的 SDK：

```
response = client.chat.completions.create(...)
```

随着应用的发展，我们可能希望从云端模型切换到本地模型，或者根据任务成本、延迟和模型能力选择不同的 Provider。

如果 Agent 的业务逻辑直接依赖每个供应商的原始响应结构，那么更换模型时，就可能需要同时修改消息处理、工具调用和执行循环。

因此，我们需要在模型服务与 Agent 之间增加一层抽象。

```python
               Agent
                 |
                 v
         统一模型调用接口
             ModelClient
                 |
        +--------+--------+
        |        |        |
        v        v        v
     OpenAI  DeepSeek  Ollama

       另一个适配器
             |
             v
         Anthropic
```

这层抽象至少应统一：

1. 模型调用入口。
2. 内部消息结构。
3. 最终答案与工具调用的表示方式。
4. 常见错误的处理边界。

但统一接口不意味着所有模型的能力完全一致。

例如，不同 Provider 可能在并行工具调用、结构化输出、多模态能力、上下文长度和流式输出方面存在差异。后续扩展时，还需要通过模型能力描述和适配器策略处理这些差异。

## 六、Agent 如何理解并执行工具调用？

这是从普通 LLM 应用进入 Agent 应用的关键一步。

### 6.1 工具调用不是模型直接执行函数

假设模型希望计算两个数字的和，它可以返回类似这样的结构化请求：

```json
{
  "type": "tool_call",
  "tool_calls": [
    {
      "id": "call_001",
      "name": "add",
      "arguments": {
        "a": 12345,
        "b": 67890
      }
    }
  ]
}
```

这是我们在应用内部定义的简化决策协议。

它表达的是模型希望调用哪个工具、使用什么参数，并不意味着工具已经执行。

接下来，Agent 需要完成以下步骤：

1. 检查工具是否已经注册。
2. 校验参数类型和必填字段。
3. 检查当前执行策略是否允许调用该工具。
4. 调用对应的 Python 函数。
5. 获取真实返回值。
6. 将执行结果交给模型。

例如：

```
def add(a: int, b: int) -> int:
    return a + b


result = add(12345, 67890)

print(result)
```

实际输出：

```
80235
```

此时，计算结果来自真实函数执行，而不是模型自行生成的文本。

### 6.2 为什么要将工具结果反馈给模型？

工具执行完成后，Agent 不应立即假设任务已经结束。

模型还需要根据结果判断：

- 结果是否足以回答用户？
- 是否还需要调用其他工具？
- 是否需要补充计算或检查？
- 是否可以返回最终答案？

因此，系统需要将工具执行结果写入消息历史，再次调用模型。

```
模型请求工具
     |
     v
程序执行工具
     |
     v
获取工具结果
     |
     v
更新消息历史
     |
     v
再次调用模型
     |
     v
继续行动或结束
```

这就是 Agent Loop 与简单工具函数调用之间的关键区别：工具不仅被执行，而且它的结果会影响模型后续的决策。

## 七、如何避免 Agent 无限运行？

只实现循环还不够。

如果模型持续请求工具，或者无法判断任务何时完成，程序就可能不断调用模型，产生不必要的成本和延迟。

因此，Agent Loop 必须有明确的控制机制。

### 7.1 最大执行步数

最简单的限制方式是设置最大执行步数：

```
max_steps = 8

for step in range(max_steps):
    decision = model.decide(messages, tools)

    if decision.type == "final":
        return decision.content

    # 执行工具并反馈结果
```

达到最大步数仍未完成任务时，系统应明确报告任务没有正常完成，而不能将其当作成功答案返回。

### 7.2 异常处理

运行过程中至少可能出现三类错误：

| 错误类型     | 例子                   | 处理方向                 |
| ------------ | ---------------------- | ------------------------ |
| 模型调用错误 | 网络异常、限流、超时   | 分类处理，必要时有限重试 |
| 工具执行错误 | 参数非法、文件不存在   | 记录错误并按策略反馈     |
| 执行控制错误 | 达到最大步数、无效决策 | 停止任务并报告状态       |

还需要注意：模型调用失败与工具执行失败是不同的问题，不应该使用完全相同的重试策略。

对于有副作用的工具，例如发送邮件、删除文件或发布文章，不能因为执行失败就不加判断地重复执行。后续应通过幂等机制、权限控制和人工确认来降低风险。

### 7.3 完成条件

一个基本 Agent 至少应该支持：

- 模型返回最终答案时正常结束。
- 达到最大步数时停止。
- 工具错误按照既定策略处理。
- 模型调用失败时向上层报告异常。
- 不允许调用未经注册的工具。

这些机制构成了可靠 Agent 的第一道控制边界。

## 八、如何验证第一个 Agent？

开发 Agent 不能只看最终回答是否正确，还要检查整个执行过程。

例如，对于计算任务，我们至少要验证：

1. 模型是否返回了正确的工具调用请求。
2. Agent 是否找到了对应工具。
3. 工具是否实际执行。
4. 工具结果是否被正确写入消息历史。
5. Agent 是否再次请求模型。
6. 模型是否基于工具结果返回最终答案。
7. 当任务一直无法结束时，最大步数限制是否生效。

### 8.1 单元测试与集成测试

本章将使用两类测试。

**单元测试**使用模拟模型，验证 Agent 的控制逻辑。

优点是速度快、成本低、结果容易复现。

**集成测试**调用真实模型 API，验证模型适配器、工具调用协议和真实模型响应。

优点是能够发现不同 Provider 的实际兼容性问题，但需要承担网络延迟、费用和模型输出不确定性。

两者不能互相替代。模拟模型测试通过，并不意味着真实模型一定会选择正确的工具；真实模型测试成功，也不意味着所有异常路径都经过验证。

### 8.2 运行日志

我们还会给 Agent 增加基本日志，记录：

- 当前执行步数。
- 模型决策类型。
- 请求调用的工具。
- 工具执行是否成功。
- 任务是否正常结束。

通过日志，我们可以观察 Agent 的执行路径，而不是只能看到最后返回的一段文本。

在后续企业级 Agent 开发中，这些基础日志还可以进一步扩展为结构化事件、任务追踪、调用耗时、Token 使用量和质量评估数据。

## 九、本章的开发路线

为了降低学习难度，本章将按照从简单到完整的顺序逐步实现。

### 第一阶段：接入真实模型

完成 Python 环境搭建，使用 SDK 调用真实 LLM API，理解不同 Provider 的差异，并建立统一的模型调用接口。

完成后，我们可以在不修改上层业务逻辑的情况下切换模型适配器。

### 第二阶段：实现模型决策协议

定义统一的 `Decision` 与 `ToolCall` 数据结构，将模型输出转换为应用内部可以处理的决策。

完成后，Agent 不再需要直接依赖某个供应商的原始响应对象。

### 第三阶段：实现工具注册与执行

建立工具注册表，定义工具 Schema，校验模型提供的参数，并执行真实的 Python 函数。

完成后，Agent 可以使用受控工具与外部能力交互。

### 第四阶段：实现 Agent Loop

将模型调用、工具执行、结果反馈和消息历史连接起来，增加最大执行步数与基本停止条件。

完成后，系统能够围绕用户目标进行多轮决策与执行。

### 第五阶段：补齐可靠性与测试

处理常见异常，增加运行日志，编写单元测试与集成测试，并比较单轮 LLM 与多步 Agent 的行为差异。

完成后，我们不仅拥有一个能够运行的 Agent，也能够观察和验证它的运行过程。

## 十、本章完成后的能力边界

完成本章后，我们已经掌握了 Agent 最基础的执行闭环：

```
用户目标
   |
   v
模型决策
   |
   v
工具执行
   |
   v
结果反馈
   |
   v
再次决策
   |
   v
完成或停止
```

但这仍然只是一个最小 Agent。

它还没有完整实现：

- 跨进程持久化与中断恢复。
- 长任务管理与任务状态机。
- 复杂任务规划与动态重新规划。
- Memory 与 Context 管理。
- DAG 与工作流编排。
- MCP 工具接入。
- 多 Agent 协作。
- 企业级权限治理、审计与可观测性。

这些能力将在后续章节逐步实现。

我们不应该在第一个 Agent 中就加入所有复杂组件，而应先让最基本的模型决策、工具执行与结果反馈机制真正运行起来。

## 十一、本章小结

实现第一个 Agent，最重要的不是使用某个特定框架，而是理解各个组件之间如何协同工作。

本章需要建立以下认识：

1. LLM 提供推理与生成能力，但不等于完整的 Agent 应用。
2. 统一模型接口可以隔离不同 Provider 的调用差异。
3. 统一决策结构可以将模型输出转换为程序能够处理的行动。
4. 工具注册中心与执行器负责将模型提出的请求转换为受控的真实操作。
5. Agent Loop 将模型决策、工具执行与结果反馈连接起来。
6. 最大执行步数、异常处理和测试机制，是 Agent 从演示程序走向可靠应用的基础。

如果用一句话总结：

**第一个 Agent 的核心，就是建立一个由模型负责决策、由程序负责执行、由真实结果驱动下一步行动，并且具有明确停止条件的运行闭环。**

当这个闭环真正运行起来之后，我们就从理解 Agent 的概念，进入了构建 Agent 应用的工程实践。
